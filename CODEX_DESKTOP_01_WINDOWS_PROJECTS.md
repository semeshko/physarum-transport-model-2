# DESKTOP-01 — Windows Application & Project Files

## Завдання для Codex

Створи першу самостійну Windows-версію Physarum Transport Model 2.0 на основі наявного застосунку: запуск із ярлика, чинний Analyze, збереження та повторне відкриття проєкту.

Це реалізаційне завдання. Проведи коротке дослідження, обери мінімальне обґрунтоване рішення, реалізуй і перевір його. Не обмежуйся документацією, демонстраційним вікном або прототипом, який залежить від запущеного dev-сервера.

Працюй за послідовністю:
Research → Reproduce → Root cause / constraints → Plan → Implement → Verify → Report.

## 1. Контекст і межі продукту

Довгострокова мета Івана — спеціалізований редактор кварталів: власна навігація, проєктні об’єкти, панелі властивостей, модифікатори, міський патерн і аналіз зв’язків. SketchUp — аналогія способу роботи, не вимога скопіювати універсальний CAD.

Поточна задача набагато вужча:

Запустити програму → завантажити територію → налаштувати Analyze → виконати розрахунок → зберегти проєкт → закрити програму → відкрити проєкт і продовжити.

Не створюй зараз новий графічний редактор. Спочатку потрібна надійна десктопна основа з документом проєкту. Це розширення наявного продукту, не окремий застосунок із продубльованою наукою.

Платформа першої версії: Windows x64. Користувач повідомив про 64 ГБ RAM і диск 1 ТБ. Не припускай модель GPU, кількість вільного місця чи потребу в усій Україні в пам’яті.

## 4. Самостійний запуск і lifecycle

Готова Windows-збірка повинна:
- запускатися подвійним кліком або через ярлик у власному вікні;
- працювати без установлених Node.js, npm, Git та без вихідного репозиторію;
- не потребувати PowerShell, npm run dev, зовнішнього browser tab або ручного localhost;
- відкривати локально упакований застосунок, а не віддалений сайт;
- запускати лише власні необхідні процеси й завершувати їх при виході;
- зберігати настройки та службові файли в дозволеному каталозі користувача, не в read-only каталозі інсталяції;
- мати зрозумілий стан запуску й помилку, а не нескінченне порожнє вікно;
- коректно обробляти повторний запуск, щоб не створювати конкуруючих записувачів проєкту.

Якщо потрібен локальний HTTP backend:
- production runtime входить у поставку та керується програмою;
- слухає тільки loopback, не 0.0.0.0;
- не покладається на вільний порт 3000 або чужий процес;
- readiness перевіряється обмеженим очікуванням;
- privileged endpoints захищені від сторонніх origins/запитів;
- дитячі процеси не залишаються після закриття чи помилки запуску.

Внутрішній loopback допустимий. Заборонена залежність від сервера, який користувач має запускати сам.

Важкі обчислення не переносити в UI або головний процес оболонки. Повторно використати чинний Analyze Worker там, де він сумісний; не створювати другий solver.

## 5. Документ проєкту v1

Побудуй невеликий, версійований і перевірюваний формат. За відсутності готового формату розглянь самодостатній JSON для малих AOI, наприклад *.physarum.json. Не створюй складний власний архів або DB без потреби.

Відокрем:
- чисті типи, валідацію та серіалізацію документа;
- платформний адаптер читання/запису;
- React-стан і відображення;
- тимчасовий runtime розрахунку.

Electron/Tauri імпорти не повинні проникати у GIS, graph, scenario чи математичні модулі.

Збережений проєкт має містити або однозначно фіксувати:
- schemaVersion, назву, ідентичність документа й версію застосунку;
- AOI, систему координат і потрібний стан камери;
- точний аналітичний snapshot: геометрії, властивості, OSM IDs, впорядковані topology anchors і provenance;
- міський контекст, який фактично використовувався, та статус відсутнього/невдалого завантаження;
- джерело, bbox, timestamp стану даних і дату отримання, якщо вони відомі; невідомі значення не вигадувати;
- transport profile, Source/Sink, magnitudes, constraints і просторові налаштування Analyze;
- фактично застосовані параметри й версію алгоритму, а не повторне читання нових defaults при відкритті;
- необхідну видимість шарів;
- останній завершений результат Analyze, якщо він є, з ознаками завершення та прив’язкою до snapshot/scenario/parameters.

Не достатньо зберегти лише URL, bbox і дві координати. Повторне відкриття не повинно непомітно отримувати новий OSM-знімок.

Не використовуй старий scratch/task-18c конвертер, який втрачав anchors. Не перетворюй anchor-aware GIS на geometry-only GeoJSON під час save/open.

Обери один авторитетний запис даних. Graph можна відновлювати штатним builder або зберігати як перевірюваний derived cache; не створюй дві суперечливі «істини». Зафіксуй fingerprint і версію побудови, перевір node/edge references.

За збігу snapshot і алгоритмів відновлюються ті самі IDs та сценарій. При несумісній версії не роби мовчазного переприв’язування: поясни проблему; міграція лише явна.

Не записуй Worker handles, DOM, MapLibre instance, Promise, API keys, cookies, runtime access tokens або весь React store. Наявність URL у документі не є дозволом автоматично завантажувати довільні ресурси чи читати локальні файли.

Перша версія документа охоплює Analyze. Design не розширюй. Не створюй можливості мовчки зберегти Design як Analyze з втратою даних: непідтримувані стани мають бути явно позначені або відповідна дія недоступна. Наявний web Design не видаляй.

## 6. Open / Save як надійні операції

Мінімальні команди у власному меню «Файл»:
- Новий проєкт;
- Відкрити… — Ctrl+O;
- Зберегти — Ctrl+S;
- Зберегти як… — Ctrl+Shift+S;
- Вийти.

Використовуй нативні файлові діалоги. Назва документа та ознака незбережених змін мають бути видимими. Новий UI і повідомлення — українською; не переробляй увесь існуючий переклад зараз.

Вимоги:
- скасований діалог не змінює поточний документ;
- перед New/Open/Close із незбереженими змінами: Зберегти / Не зберігати / Скасувати;
- невдале або скасоване збереження не закриває й не замінює документ;
- запис спочатку готується окремо, потім безпечно замінює ціль; перевір Windows-семантику та збереження попередньої валідної копії при помилці;
- serialized writes та revision guard не дозволяють старому async save позначити нові зміни як збережені;
- відкриття проходить parse → validate → prepare → commit state; помилка не руйнує вже відкритий проєкт;
- розмір, вкладеність і кількість об’єктів обмежуються зрозумілими перевірками;
- unsupported schema, пошкоджений файл, permission denied та помилка запису мають зрозумілі повідомлення;
- шляхи з пробілами й українською кирилицею працюють.

При заміні проєкту скасуй належні йому OSM-запити та Worker run. Старі callbacks не повинні дописати дані в новий проєкт. Скасований користувачем Open не знищує чинний runtime.

Результат зберігається тільки як узгоджений завершений snapshot. Не серіалізуй running/paused як відновлювану живу симуляцію. Після відкриття не запускай розрахунок автоматично. Зміна наукового input інвалідує старий результат за чинними правилами. Рух камери або зміна видимості не повинні міняти науковий fingerprint.

Повний Undo/Redo, автозбереження історії, session recovery і кілька одночасних документів — наступні задачі. Зараз не будуй їх замість коректних Open/Save.

## 7. Analyze і дані: зберегти поведінку

Відтвори на desktop:
реальні OSM-дані → штатний anchor-aware adapter → graph → profile → scenario → існуючий Analyze Worker → відображення.

Збережи Run/Pause/Resume/Reset, перемикання профілів, вибір терміналів і stale-run protection. Не перемикай опціональну нормалізацію Task 17 або інші defaults під приводом десктопної міграції.

Не змінюй one-way, rail/tram semantics, costs, формули, convergence thresholds або topology policy. Виявлені сторонні проблеми документуй окремо; лише реальний блокер цього завдання виправляй мінімально з тестом.

Збережи роботу OSM API routes і propagation скасування. Не повертай browser-direct запити як обхід пакування. Не розширюй allowlist постачальників без потреби.

Карта, MapLibre worker, simulation worker, public assets та потрібні bundled dependencies повинні працювати після пакування, а не лише в dev. Не прибирай MapLibre worker fix без доведеного еквівалента.

Поточну підкладку залишити. Якщо її доступ потребує конфігурації, повідом і підтримай штатне налаштування, а не змінюй провайдера автоматично.

## 8. Чесний offline-режим

Інстальований застосунок, Open/Save та повторний Analyze збереженого snapshot повинні працювати без інтернету й без вихідного репозиторію.

Це не вимога завантажити офлайн усі тайли України. Нові OSM-запити й незбережена підкладка можуть потребувати мережі.

Якщо онлайн-підкладка недоступна, не блокуйте документ, власні GeoJSON-шари й solver очікуванням remote style. Потрібен мінімальний локальний нейтральний стиль/фон зі статусом «Підкладка недоступна», а не непомітна заміна dataset. Показати геометрію проєкту й наявний результат має бути можливо.

Не використовуй випадково прогрітий browser cache як доказ offline-працездатності. Перевір холодний запуск без мережі. Не роби забороненого bulk caching тайлів.

## 9. Безпека десктопної межі

Для Electron перевір актуальні офіційні security recommendations. Мінімум:
- nodeIntegration: false, contextIsolation: true, sandbox: true;
- не вимикати webSecurity, перевірку сертифікатів чи CSP для усунення помилки;
- вузький typed preload/IPC API для конкретних операцій;
- валідація sender/origin, payload і прав на файлові операції;
- ніяких exposed fs, shell, child_process або універсальних readFile/writeFile/IPC мостів;
- файл вибирається через довірений діалог, а подальший Save прив’язаний до перевіреної сесії документа;
- зовнішні посилання не можуть замінити trusted renderer; дозволені URL відкривати лише контрольовано;
- не виконувати scripts/HTML з імпортованих даних, не логувати секрети.

Для Tauri, якщо він обраний за обґрунтованим рішенням, забезпеч еквівалентні capability-обмеження.

Розділи непривілейоване відображення, доступ до файлів і обчислення. Не розв’язуй проблеми Worker або локального backend розширенням привілеїв усього renderer.

## 10. Збірка й поставка

Обери один підтримуваний packaging tool. Для Electron спочатку перевір Electron Forge; інший варіант допустимий за конкретної потреби. Зафіксуй runtime-версію та lockfile, не роби неконтрольоване оновлення решти стеку.

Потрібні:
- документована dev-команда для розробника;
- команда production packaging;
- Windows x64 installer для локального тестування;
- запакований застосунок, який запускається з ярлика та без глобального node.exe;
- усі його frontend/server/Worker/static ресурси;
- запис версії, базового SHA і шляхів вихідних артефактів.

Перевір, що package не читає source tree або node_modules з робочого каталогу. Усі записи мають йти поза каталогом інсталяції.

Якщо сертифіката підпису немає, створи явно unsigned test build і повідом про це. Не вигадуй підпис і не вимикай захист Windows. Auto-update та публічний реліз поза задачою.

Інсталятор, build outputs, user projects, cache, secrets і scratch не комітити в Git. Зберігати тільки код, lockfile, конфігурацію, тести та документацію.

## 11. Перевірки

Спочатку зафіксуй фактичний baseline. Не вважай історичний test count критерієм.

Детерміновані тести мають перевірити:
- round-trip документа зі збереженням topology anchors, properties, IDs і параметрів;
- відновлення сценарію, constraints і завершеного результату з fingerprint;
- однаковий input і чисельно еквівалентний повторний Analyze у задокументованому допуску;
- пошкоджений/завеликий документ, невідомий schemaVersion, неправильні references;
- cancel Open/Save, save failure, dirty state, конкуренцію async saves;
- старий Worker/OSM callback після зміни проєкту;
- відсутність прихованого refetch при відкритті;
- дозволені й відхилені IPC-операції;
- packaged resource paths і lifecycle локального backend, якщо він є.

Заверши npm test, npm run lint, npx tsc --noEmit, npm run build та git diff --check, а також нові desktop/package checks. Не приховуй попередні warnings.

Обов’язковий desktop smoke на зібраному Windows-застосунку:
1. Установити в тестовий каталог, запустити з ярлика без dev-сервера.
2. Перевірити карту, власні шари, WebGL і Workers.
3. Завантажити малу реальну OSM-територію; дата й невдалий context load не приховуються.
4. Pedestrian і Motor: вибрати Source/Sink, Run, Pause/Resume, Reset.
5. Зберегти «Квартал Львів — тест.physarum.json» у шляху з кирилицею та пробілами.
6. Закрити програму; перевірити завершення її процесів.
7. Відкрити проєкт знову: дані, параметри, камера й результат відновлені, нічого не перезавантажено з OSM.
8. Повторити розрахунок на збереженому input і зіставити результат.
9. Змінити термінал/профіль: старий результат інвалідовано, документ dirty.
10. Перевірити Save As та всі варіанти unsaved-changes діалогу.
11. Відкрити пошкоджений файл: поточний документ залишився неушкодженим.
12. Холодний запуск offline: проєкт, шари та повторний розрахунок працюють; відсутність підкладки пояснена.
13. Перевірити запуск без доступу до source tree і без Node/npm у PATH, бажано на чистому Windows-профілі/VM.
14. Перевірити повторний запуск і відсутність конфлікту з зайнятим портом 3000.
15. Перевірити, що існуючий web Analyze не зламаний.

Коли native dialog не автоматизується, документуй ручну перевірку. Не зараховуй запуск у звичайному Chrome як desktop QA. Не називай пакет готовим до приймання без фактичного запуску Windows-збірки. За обмежень середовища окремо подай готові артефакти, неперевірені пункти та точні дії для Івана.

## 12. Git, звіт і STOP

Роби невеликі логічні коміти на desktop-гілці. Не переписуй історію review-гілки й не зливай нічого в main. За наявного дозволеного origin можна push лише desktop-гілки після перевірки diff; merge лишається окремим рішенням Івана.

Поверни:
- обрану оболонку й спосіб пакування backend з коротким обґрунтуванням;
- base SHA, нові SHA, branch і working tree;
- схему процесів та межу привілеїв;
- формат документа: що збережено, що не підтримується, version policy;
- точні команди dev/build/package;
- фактичний шлях до інсталятора, розмір, checksum і signed/unsigned статус;
- виміряні запуск, пам’ять та save/open на зазначеному dataset, без вигаданих оцінок;
- результати автоматичних і desktop-перевірок окремо;
- коротку інструкцію користувачу: встановлення → перший проєкт → збереження → повторне відкриття;
- відомі обмеження й одну рекомендовану наступну задачу.

Використай один звіт docs/desktop-01-report.md і коротку специфікацію формату, якщо окремий файл справді потрібний. Не замінюй реалізацію серією великих research-звітів.

УСПІХ: Іван запускає встановлену програму, працює в Analyze, зберігає реальний проєкт і відновлює його після повного закриття без npm, PowerShell або повторного завантаження аналітичних даних.

ПОЗА ОБСЯГОМ: UE5, новий renderer, full CAD, моделювання фасадів, нові модифікатори геометрії, Prediction, генерація авторського патерну, corridor extraction, зміни Design-науки, directed Physarum, rail solver, нові basemap/terrain providers, автозавантаження України/планети, cloud sync, plugins, auto-update.

STOP після цієї робочої десктопної версії та звіту. Не починай наступний модуль без погодження.
